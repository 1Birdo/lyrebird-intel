01

What each figure counts

  • Events — the per-day event counts for addresses seen in the window. One attacker action can emit several events, so this is never labelled “attacks”.
  • Source addresses — distinct public addresses. Private, loopback, reserved, multicast and link-local sources are excluded before anything is recorded.
  • The funnel — each bar counts addresses meeting a strictly stronger condition than the one above it, as a share of the first bar.
  • Credential attempts and distinct pairs are reported separately and never merged; conflating them once overstated this corpus by a wide margin.
  • Payload hosts exclude addresses that are not routable from the internet. Mirai templates the victim's own LAN gateway into its fetch, so counting those would put an unreachable address at the top.
  • Countries come from an offline table and are counted per address.
  • Variant families — samples whose bytes differ only in the parts a key normalises (filenames, addresses, ports, tokens) share a family; every hash is listed, one archive per family is packaged.
Some figures are lifetime totals for addresses active in the window rather than totals for the window itself — a per-address rollup covers the whole retention period. Credential attempts, sessions and payload fetches are of that kind, and no trend is ever computed by subtracting two of them.
02

What is deliberately not published

Anything the sensor said back. No banners, no fake command output, no filesystem contents, no prompts. A transcript of the emulation's replies is a fingerprinting cookbook — publish it and anyone can build a reliable detector for this honeypot, after which it stops seeing anything worth publishing. The guarantee is structural: the generator only ever reads attacker-supplied fields, and a second, independent guard refuses to write any file that carries an internal string.

Also absent: anything describing the deployment — its address, host, provider, software versions, listening-port inventory or uptime. That describes the sensor, not the attacker.

An admission against interest: aggregate statistics are themselves a weak fingerprint of this sensor. That is the price of publishing anything at all. It is far weaker than publishing responses would be, and it is a reason never to add response-side metrics later on the grounds that “we already publish statistics”.

03

How to read this data

This dataset is the record of what an internet-facing honeypot was sent. Every row is something an attacker did to a machine that was pretending to be vulnerable. It is easy to read a honeypot feed and claim far more than it supports; this is about reading it honestly.

The one rule

Move in this order and never skip a step: observed fact → technical interpretation → confidence → investigation hypothesis.

  • Observed fact — what is literally in the data. “203.0.113.9 sent root/admin to the SSH port 412 times in 90 seconds.”
  • Technical interpretation — what that behaviour is, in neutral terms. “A credential brute-force against SSH.”
  • Confidence — how sure the interpretation is, and why. “High: the rate and the wordlist are characteristic.”
  • Investigation hypothesis — what you would check next, phrased as a question. “Does this address appear in other feeds as a known SSH brute-forcer?”

The failure mode is jumping straight to a story — “a threat actor is targeting us” — from a fact that only supports “a bot tried common passwords”. This feed supports the second sentence, rarely the first.

The behaviour ladder

behaviourwhat it looks like in this datawhat it meanswhat it does not mean
Background noiseA handful of connections, no login, or a single banner grab across many portsUntargeted internet-wide measurement — researchers, census scanners, worms looking for a handshakeNot an attack on you; the same packets hit every address
ScanningOne source touching many ports, or one port across a short window; protocol probes on the wrong portReconnaissance — mapping what answersInterest in you specifically; scanners hit whole ranges
Brute-forceMany auth attempts to one service, common username/password pairsAutomated credential guessingA compromise — the credentials are tried, not known to work
ExploitationA specific request matching a known CVE or a command-injection payloadAn attempt to run code or gain access via a named weaknessThat it succeeded — the service was emulated; nothing was actually exploited
Post-exploitationCommands run after a shell is offered: a second stage, persistence, killing rivals, reading system filesThe playbook a bot runs once it thinks it is inThat any real system was compromised — the “shell” was a decoy that recorded the script

The last row is the valuable one: it is the attacker's own automation, captured. But read it for what it is — what the bot would have done — not as evidence that it did it to a real host.

Confidence, honestly

  • High — the behaviour is unambiguous and self-evidencing: a payload that matches one specific CVE, a login rate no human produces.
  • Medium — consistent with a technique but with benign explanations: a single odd request could be a broken client as easily as a probe.
  • Low / inconclusive — say so and stop. A feed like this has a long tail of traffic that is simply unexplained, and inventing a reason for it is the most common way these datasets get misread.

What this data cannot tell you

  • Who. Source addresses are not identities. This dataset makes no attribution claims — not to a person, a group, or a country — and neither should anything built from it.
  • Why you. Almost none of this is aimed at anyone specifically. A honeypot sees the same broad, automated hostility every public address sees.
  • That anything was breached. “An exploit was attempted” is a fact; “a system was compromised” is a different claim that this data, on its own, does not make.

Using it to check your own systems

  1. Take the indicators — addresses, credential pairs, sample hashes, payload URLs.
  2. Check whether any appear in your own logs.
  3. If they do, that is a fact worth an investigation hypothesis on your side — begin the ladder again with your evidence, not this one's.

The value of a honeypot feed is as a set of things to look for in ground truth you control, not as a set of conclusions to import.

Reproducing a figure

Clone the repository, or fetch the CSVs raw. Each is RFC 4180 with a header row; attacker text is quoted, never rewritten.

recompute this
git clone https://github.com/1Birdo/lyrebird-intel.git
tail -n +2 iocs/source-ips.csv | wc -l                        # addresses
awk -F, 'NR>1 && $8>0' iocs/source-ips.csv | wc -l           # ran commands
sort -t, -k3,3nr credentials/attempted-credentials.csv | head  # top pairs
cut -d, -f9 iocs/source-ips.csv | tr '|' '\n' | sort | uniq -c   # CVEs
